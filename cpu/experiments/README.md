# CPU experiment archive

## Purpose

Keep reproducible records of a rejected contour-pruning experiment and the
selected prefix-cache budget. Dual component pruning was rejected because its
connected-component and pixel-remapping costs exceeded the contour work saved.
The cache-stripe probe reproduces the threshold microbenchmark used to select
the detector's configurable 2 MiB prefix budget.

## Scope

These standalone probes are excluded from every production build. Dual pruning
uses OpenCV's public APIs and the repository's unchanged
`hybrid::find_quad_candidates`; the cache probe compiles the maintained threshold
helper. No CUDA toolkit, GPU, or test framework is needed. The runners do not
change detector defaults or expose a supported API.

## Current state

The dual-pruning implementation and parameters match the rejected scratch probe,
with names and formatting cleaned up. Given the detector's minimum contour
point count `P`, dual pruning:

1. Removes 8-connected foreground components for which `8 * area < P`.
2. Labels the inverse with 4-connectivity, then fills background components for
   which `8 * area < P`, except components whose bounding boxes touch any image
   border. Border-touching background is never filled.
3. Calls the unchanged contour extraction and quadrilateral filtering.

A second variant performs only the background step. The bound comes from
counting directed neighboring pixel states, at most eight per component pixel.
Filling a hole may merge an interior foreground island with the enclosing
foreground, so this bound alone is not presented as a complete proof of contour
path or ordering preservation. The probe compares the exact ordered
`RETR_LIST`/`CHAIN_APPROX_NONE` eligible contours, including every point and cyclic
start, and separately compares the actual quadrilateral candidates and their
associated full contour paths. Compatibility is supported by the tests below;
general equivalence remains unproven.

### Build and correctness reproduction

Run from the repository root, in an environment containing the pinned OpenCV
4.14.0 build. The repository's `aruco3-cuda:dgx-spark-mounted` container supplies
it under `/opt/opencv`.

```bash
cmake -S cpu/experiments -B build/cpu-dual-prune-archive \
  -DCMAKE_BUILD_TYPE=Release -DOpenCV_DIR=/opt/opencv/lib/cmake/opencv4
cmake --build build/cpu-dual-prune-archive -j2
taskset -c 0-3 build/cpu-dual-prune-archive/aruco3cpu_dual_prune_probe
taskset -c 0-3 build/cpu-dual-prune-archive/aruco3cpu_dual_prune_probe exhaustive
```

The default mode performs **69,918** exact contour and candidate comparisons:

- Random square binary images with dimensions 1 through 12, densities
  1/5/15/35/50/65/85/95/99 percent, and 60 samples per density and dimension.
  Minimum contour lengths are 1/8/9/16/24/32/64/128.
- 3,000 mixed line/rectangle/circle 64x64 images, followed by concentric nested
  rectangles. Minimum lengths are 9/16/32/64/128/256. The random seed is 81753.

QA independently added exhaustive input enumeration using the same pruning and
comparison functions. It checks every binary image of dimensions 3x3, 4x4, 5x3,
and 3x5 at minimum lengths 9/17/25/33. All **526,336** comparisons passed. This
enumeration is archived as the `exhaustive` mode. Both modes return nonzero on a
discrepancy. A contour mismatch also writes `dual-prune-failure.png` and
`dual-prune-failure-filtered.png` into the current directory.

### Timing reproduction

The four timing inputs are generated by the existing extended CPU corpus
generator. If `data/cpu-experiment` is absent, the following generates the corpus
and checks one scene before running this experiment:

```bash
cmake -S cpu/standalone -B build/cpu-opt \
  -DCMAKE_BUILD_TYPE=Release -DOpenCV_DIR=/opt/opencv/lib/cmake/opencv4 \
  -DARUCO3CUDA_BUILD_TESTS=OFF
cmake --build build/cpu-opt --target aruco3cuda_cpu_benchmark -j2
build/cpu-opt/cpu/aruco3cuda_cpu_benchmark \
  --input-dir data/cpu-experiment --generate \
  --filter cpu_1280x720_n4_clean --variants opencv --iterations 1 --warmup 0
```

Then run the archived timing mode:

```bash
taskset -c 5 build/cpu-dual-prune-archive/aruco3cpu_dual_prune_probe \
  benchmark data/cpu-experiment
```

The measured interval includes inversion, connected-component labeling,
statistics, pixel remapping, contour extraction, and quadrilateral filtering,
for all three adaptive windows 3/13/23. Loading and thresholding (offset 7) occur
outside timing. Full-resolution ArUco3-disabled extraction uses the detector's
default `minMarkerPerimeterRate=0.03`; minimum contour lengths are therefore 38
at 1280x720 and 115 at 3840x2160. Every input is checked against unpruned contour
and candidate results before timing.

Variant 0 is unpruned, variant 1 background-only, and variant 2 dual pruning.
The probe uses one OpenCV thread, three warmups and eleven measured iterations
per variant. The median selects sample 6 after sorting; nearest-rank p95 and p99
both select sample 11. Variants are measured sequentially rather than alternating.
These are exploratory rejection measurements, not the formal repeated detector
benchmark. CUDA kernel time does not apply to this host-only experiment.

`dual_prune_probe.cpp` is an independently derived experiment under this

### Cache-stripe reproduction

The same standalone build also produces `aruco3cpu_cache_stripe_probe`. Its
default correctness mode compares the three budgets 0/2 MiB/4 MiB against
OpenCV on white and random strided ROIs, fractional offsets and odd image sizes.
The benchmark rotates the route order, uses ten warmups and eighty samples,
and prints each route's p50/p95/p99 plus the planned scratch payload. The payload
is derived from matrix geometry; it is not RSS or allocator capacity.

```bash
taskset -c 0-3 build/cpu-dual-prune-archive/aruco3cpu_cache_stripe_probe correctness 1
taskset -c 0-3 build/cpu-dual-prune-archive/aruco3cpu_cache_stripe_probe correctness 4
taskset -c 5 build/cpu-dual-prune-archive/aruco3cpu_cache_stripe_probe benchmark 1
taskset -c 5-8 build/cpu-dual-prune-archive/aruco3cpu_cache_stripe_probe benchmark 4
```

Repeat the benchmark in three independent processes to reproduce the aggregation
method. See [threshold design and results](../cpu_threshold.md) and the archived
[raw measurement records](../../docs/measurements/2026-11-17-cpu-cache-stripe/README.md).
The current reproduction runner includes the maintained helper's subsequent
alias/fallback robustness checks; historical exploratory measurements used its
equivalent scratch implementation before those checks were added.

## Goals

- Preserve enough source, parameters and raw results to reproduce the rejection.
- Preserve the selected threshold budget's paired comparison and memory geometry.
- Keep the archived experiment separate from measured production binaries.
- Avoid repeating an expensive experiment without a new reason to expect a gain.

## Open questions

- Whether a formal proof can establish preservation of every eligible contour
  path and enumeration order, beyond the tested inputs.
- Whether a substantially different component representation could amortize its
  cost in another application. No such improvement is claimed or implemented.
