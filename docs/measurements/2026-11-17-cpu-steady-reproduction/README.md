# Final CPU measurement orchestration

## Purpose

Preserve the one-off orchestration scripts used for the final steady-state
measurements. A license comment was added to the primary orchestrator at
archival; its executable statements are unchanged. The maintained CLIs and
per-run environment records remain the source of detector settings, input
hashes and executable hashes.

## Scope

Run from the repository root inside the documented CPU container, with the
portable and native executables and input corpora already prepared. These
scripts assume the paths and reserved performance cores used in this experiment.
They refuse existing result files. Use a separate checkout or new destinations
for reproduction; do not overwrite the archived evidence.

## Current state

Generated measurement results, logs and environment captures referenced below
are local-only and ignored by Git. This document and reproduction sources remain
version-controlled; a fresh checkout does not contain the recorded outputs.

Copy the `cpu-steady-*.py` files to ignored `build/`. Run
`python3 build/cpu-steady-runs.py` for the ten primary groups. The
`cpu-steady-after-primary.py` script waits for that process to finish, verifies
the last summary, and starts native, video, resource, stage and quiet-confirmation
groups in sequence. It was launched concurrently with the primary orchestrator;
only the orchestrator waits concurrently, not another detector benchmark.

The quiet-confirmation script requires `build/cpu-steady-qa-complete`, represented
here by qa-complete.json (local `qa-complete.json`), and verifies its recorded source
hashes. The historical JSON is local-only; a fresh checkout must create a new
marker with the completed validation run's source hashes. Create that marker only
after all validation work finishes. This is a
measurement scheduling gate, not a substitute for running the tests.

The extra-run orchestrator now stops after stage profiling at
`build/cpu-steady-ready-for-failure-fix`. The final review found a sparse-cache
allocation-recovery issue while primary measurements were still running. The
[repair and verification](../2026-11-17-cpu-steady-recovery-validation/README.md)
were applied only after every original-source timing group finished. The
coordinator then refreshes the QA marker to the repaired source/binaries and
creates `build/cpu-steady-failure-fix-complete` to release quiet confirmation.
The primary/source-stage records preserve this distinction. Reversing the
recorded repair patch reconstructs the measured pre-repair sparse source;
ordinary successful-frame arithmetic is identical.

Inputs are generated by the maintained [benchmark](../../../cpu/benchmark.cpp),
[quality renderer](../../../tools/cpu_quality/quality_scenes.md), and
[high-ID generator](../../../cpu/experiments/generate_high_id_corpus.md).
Each output directory records the actual command, inputs, source and executable
hashes. Scripts retain the original output names and container paths; they are
an execution record rather than a portable benchmark framework.

[aggregate_report.py](aggregate_report.py) reads the completed primary, native,
video, resource and quiet groups, checks record counts and compatibility, and
writes `build/cpu-steady-report-data.json`. Its recorded output is
report-data.json (local `report-data.json`). It aggregates process percentiles without
pooling samples and compares quiet results with the same input hashes from the
earlier full corpora. Per-stage diagnostic values remain in their raw records.

## Goals

- Keep detector performance jobs sequential on the reserved core budget.
- Preserve process repetition, unfavorable cases and exact compatibility checks.
- Make the independent validation-to-quiet-measurement boundary explicit.

## Open questions

- Unrelated host services and the host power policy were retained. These scripts
  do not establish a controlled machine-wide power or frequency experiment.
