# Benchmark 報告: CPU 基準と hybrid 経路

- 測定日: 2026-08-28
- 対象: WP-4.1 の転送最適化を適用した実装

## 目的

[評価計画](evaluation-plan.md) が定める crossover point を、現時点で実装がある 2 経路について求めます。CUDA 化に投資を続ける価値があるかを、Phase 3 (GPU decode) へ進む前に判断するための材料です。

## 対象範囲

`CPU` 経路 (OpenCV ArUco3) と `Hybrid` 経路 (GPU で前処理と二値化、CPU で候補抽出と decode) を比較します。`CUDA-E2E` と `CUDA-Resident` は未実装のため対象外です。

## 測定した区間

**検出のみです。画像の読み込みと checksum は含みません。**

この点は本報告以前の測定と異なります。従来 `measure_image` は 1 反復ごとに `cv::imread` と `sha256_file` を呼んでおり、測定区間の 58% から 85% が PNG の復号でした。

| 画像 | imread | sha256 | detectMarkers | 検出以外の割合 |
| --- | --- | --- | --- | --- |
| clean_1280x720_n1_s128.png | 1.834 ms | 0.031 ms | 1.168 ms | 61.5% |
| clean_1280x720_n4_s128.png | 1.941 ms | 0.036 ms | 1.403 ms | 58.5% |
| degraded_1280x720.png | 8.875 ms | 4.893 ms | 2.465 ms | 84.8% |

実時間処理では PNG を復号しません。検出時間を比べる測定として成立していなかったため、読み込みを初期化側へ移しました。JSONL の `schema_version` を 3 へ上げています。version 2 以前の結果は同じ key が違う区間を指すため、混ぜて集計できません。

### 固定する CPU core

**性能 core へ固定します。** 性能 core と効率 core が混在する機では、どちらで測るかで値が 2 倍変わります。

| 機体 | core 構成 | 測定に使う CPU |
| --- | --- | --- |
| DGX Spark GB10 | Cortex-X925 x10 (性能)、Cortex-A725 x10 (効率) | 5 (X925) |
| RTX 5070 Ti の機 | 4.80GHz x2、4.70GHz x6 (性能)、4.60GHz x12 (効率) | 2 (4.70GHz) |
| Jetson AGX Orin | Cortex-A78AE x12 (均一) | 0 |

DGX Spark と RTX の機はいずれも CPU 0 が異なる種別です。DGX Spark の CPU 0 は効率 core、RTX の機の CPU 0 は性能 core です。番号だけで揃えると別種の core を比べることになります。

本報告の初版は DGX Spark を CPU 0 (効率 core) で測っており、GPU 側の優位を過大に評価していました。差の大きさは [core 種別の影響](#core-種別の影響) に示します。

再現手順は [測定の再現](#測定の再現) にあります。生の結果は `docs/measurements/` にあります。

### Step 1: 何を並列にして、何を並列にしなかったか

累積される 5 つの量は要素ごとに閉じており、要素間に依存がありません。倍精度の演算は被演算子の決定的な関数なので、**どの thread が計算しても bit 表現は変わりません**。

| 段階 | 並列度 | 理由 |
| --- | --- | --- |
| patch の切り出し (最大 169 要素) | 要素ごと | 持ち回りの深さが 1 なので閉じた式に書ける |
| 勾配と 5 つ組 (最大 121 要素) | 要素ごと | 要素間に依存が無い |
| 累積 (5 本の鎖) | 5 lane | **順序を変えない。** 各鎖の中では添字の昇順を保つ |
| 解と位置の更新、分岐 | thread 0 | 累積の結果だけで決まる |

逐次の連鎖は 1 反復あたり 2299 命令 (121 要素 x 19 命令) から、およそ 140 命令 (19 + 121) へ縮みました。

### Step 2: Otsu の漸化式は並列化できない

Otsu も 3 相に分けましたが、**中央の漸化式は並列化してはなりません**。

| 相 | 並列度 | 理由 |
| --- | --- | --- |
| 重心 `mu = Σ i*h[i]` | 256 要素を並列 | 全項が整数。上限 2.7e11 は 2^53 に収まるため**丸めが 1 度も起きず、加算順序を変えても bit 同一** |
| 漸化式 | **thread 0 の逐次** | 下記 |
| 分離度と最大の探索 | 256 要素を並列 | `(mu, q1_i, mu1_i)` の純関数 |

漸化式が並列化できない理由は 2 つあります。第 1 に `p_i = h[i]*scale` が丸められた倍精度なので `q1` の累積は順序に依存します。第 2 に、より重大な罠として、**guard で飛ばした反復では `mu1` が正規化されない状態のまま持ち越されます**。

```
mu1 *= q1;                    // 前回の q1 を掛ける
q1 += p_i;
if (guard) continue;          // ここで抜けると mu1 は正規化されないまま残る
mu1 = (mu1 + i*p_i) / q1;     // 通常はここで正規化される
```

つまり `mu1` は「連続して何回飛ばしたか」に依存する経路依存量です。`q1` を並列 scan で作ってから `mu1` を復元する形は必ず壊れます。

逐次に残したのは `mu1 *= q1`、`q1 += p_i`、`mu1 = (...)/q1` だけで、**倍精度の除算が 1 反復あたり 2 回から 1 回へ減りました**。除算は倍精度で最も待ち時間が長く、ここが連鎖の長さを決めていました。

最大の探索では、逐次版の 3 つの性質を厳密に守っています。`max_sigma` の初期値が 0.0 で更新が厳密な大なりであることから、(1) `sigma` が 0 以下の階調は選ばれない、(2) 同値なら小さい階調が残る、(3) 一度も更新されなければ 0 を返す、が導かれます。畳み込みは `(sigma が大きい, 階調が小さい)` の辞書式にしました。

### 検出 0 件では逆に遅くなった

DGX Spark で 0.572 から 0.615 ms、Jetson で 1.053 から 1.124 ms へ増えています (RTX は変化なし)。S10 が共有 memory を 1 block あたり約 5.5 KB 使うため、**検出が 0 件でも block を起こす費用が上がった**ためです。

S10 の block 数は評価計画の上限 (マーカー 16 枚 = 64 隅) を 1 波で覆う 64 に絞りました。これを超える隅は block が跨ぎながら処理します。

**当初は隅の上限 (4096) だけ block を起こしていました。** その形では Jetson AGX Orin で検出 0 件でも 1.05 から 7.07 ms へ 7 倍悪化しました。共有 memory のため 1 SM に載る block が限られ、起動が波に分かれたためです。3 機で測らなければ気付けませんでした。

### 検出 0 件の 0.572 ms は半分以上が kernel 起動の費用

1 frame あたりの kernel 起動数は **124 個 + memset 1 個**で、入力に依存しません。すべての grid が host 側の定数から決まり、device 上の候補数は kernel 内の早期 return でしか効かないためです。

DGX Spark で 1 起動あたりの費用を測ると **1.888 us** でした。124 起動で 234 us になり、これは検出 0 件の最小値 427 us の **55%** に当たります。残る 193 us のうち名前を付けられるのは 110 us (pyramid の 1 段目 26 us、resize 9 us、適応的二値化 6 個で計 30 us 程度、ほか) で、**残り約 110 個の kernel は 1 個 2 から 7 us であり、1 起動の費用と同じ桁です。したがって「起動の費用」と「実際の仕事」はこの粒度では分離できません。**

RTX 5070 Ti の 0.209 ms も、0 件の 3 場面が画像内容によらず 1.5% 以内で揃うことから起動列で決まっていると見ていますが、**1 起動あたりの費用はこの機ではまだ測っていません。**

### Hybrid が依然として最も速い場面がある

きれいな場面では Hybrid (GPU 前処理 + CPU decode) が最も速いままです。1280x720 マーカー 4 枚で DGX Spark は Hybrid 0.381 ms、CUDA-Resident 1.351 ms、CPU 0.701 ms でした。CPU 側の `cv::cornerSubPix` は隅が少なければ十分速く、GPU の固定費を払う価値がありません。逆に noise では Hybrid 2.448 ms に対し CUDA-Resident 0.700 ms であり、候補が増えると立場が入れ替わります。

**したがって現時点で「常に最速の経路」はありません。** 場面によって 3 経路の順位が変わります。

## 読み取れること

### 1. 転送の最適化で優位が 2 倍近くになった

WP-4.1 で、8 回の同期転送を stream 上の非同期転送へ変え、受け取り先を pinned memory にしました。GPU 段は DGX Spark で 0.461 ms から 0.206 ms、RTX 5070 Ti で 0.386 ms から 0.116 ms へ下がりました。

| 場面 (1280x720 マーカー 4) | 最適化前の比 | 最適化後の比 |
| --- | --- | --- |
| DGX Spark GB10 | 0.91 | **0.54** |
| RTX 5070 Ti | 0.92 | **0.48** |
| Jetson AGX Orin | 2.00 | 1.22 |

変更前は複製そのものより、8 回の blocking 呼び出しの費用 (1 回あたり約 25 µs) が大きく効いていました。詳細は [host と device の間の memory 受け渡し](design/memory-transfer.md) にあります。

### 2. 効きが出るのは CPU 段が小さい場面

hybrid の CPU 段は場面の内容に強く依存します (0.04 から 2.2 ms)。GPU 段が 0.12 から 0.27 ms で安定しているため、CPU 段が小さい場面ほど比が下がります。

ぼけの場面 (検出 0 件) で DGX Spark 0.46、RTX 5070 Ti 0.32 と最良です。noise の場面では CPU 段が 2.2 ms を占め、比は 0.90 前後にとどまります。**Phase 3 で decode を GPU へ移す価値はここにあります。**

### 3. 解像度が上がるほど有利

両 Blackwell 機で 1920x1080 と 3840x2160 の比は 0.47 から 0.52 です。640x480 では 0.62 と 0.73 で、優位が小さくなります。

### 4. Jetson Orin は条件によって逆転する

最適化前は全条件で CPU が速く、比は 1.19 から 2.00 でした。最適化後は 0.64 から 1.65 になり、3840x2160 とぼけの場面で hybrid が 1.6 倍速くなります。一方 640x480 では依然 1.65 倍遅いままです。

Orin の GPU 段はばらつきが大きく (0.64 から 2.54 ms)、他 2 機の 0.12 から 0.27 ms と比べて不安定です。原因は特定できていません。

### 5. 単体 GPU でも転送費用は小さい

RTX 5070 Ti で `M-Device` と `M-Pageable` の差は 1280x720 で 0.040 ms、3840x2160 で 0.293 ms です。統合 GPU の DGX Spark では 1280x720 で 0.155 ms と、むしろ大きく出ます。理由は特定できていません。

### 6. 起動の費用は依然として大きい

CUDA の文脈生成は最適化の対象外であり、1 枚目の結果が出るまでは CPU 経路の 30 倍から 40 倍です。相殺には 680 frame から 810 frame を要します。単発の検出では CPU 経路が有利という結論は変わりません。

### 7. GPU 段の大半は依然として転送である

転送最適化の後も、kernel 実行だけなら DGX Spark で 0.099 ms、GPU 段全体は 0.206 ms です。半分は転送のままです。統合 GPU で managed または mapped memory を使えば複製自体を省けますが、未実装です (WP-4.2)。

### core 種別の影響

DGX Spark を効率 core (Cortex-A725) と性能 core (Cortex-X925) の両方で測りました。効率 core の生データは schema_version 3 で取得したものであり、起動の費用を含まないため `docs/measurements/` へは残していません。

| 場面 | 効率 core CPU | 効率 core 比 | 性能 core CPU | 性能 core 比 |
| --- | --- | --- | --- | --- |
| 1280x720 マーカー 4 | 1.377 ms | 0.76 | 0.700 ms | 0.91 |
| 3840x2160 マーカー 4 | 3.816 ms | 0.46 | 1.722 ms | 0.69 |
| 640x480 マーカー 4 | 1.052 ms | 1.03 | 0.554 ms | 0.93 |

CPU 経路は core 種別で約 2 倍変わります。GPU 段も kernel 起動が CPU 側の処理であるため 0.69 ms から 0.46 ms へ下がります。結果として**効率 core で測ると GPU の優位が実際より大きく見えます**。3840x2160 では 2.17 倍と 1.45 倍で、結論の印象が変わる差です。

実運用で検出を効率 core へ固定することは考えにくいため、性能 core の値を本報告の主結果とします。

## 判断

**Phase 3 (GPU decode) へ進むべきです。**

- 転送の最適化 (WP-4.1 の一部) だけで、DGX Spark と RTX 5070 Ti の優位が 1.1 倍から 2 倍前後へ広がりました。Jetson Orin も条件によっては逆転します。
- 残る費用の内訳は明確です。GPU 段 0.206 ms のうち kernel 実行は 0.099 ms で、残り半分は依然として転送です。CPU 段は 0.04 から 2.2 ms で、場面の内容に強く依存します。
- **CPU 段を GPU へ移す (Phase 3) と、転送も同時に不要になります。** 効果が最も大きい場面 (noise、複合劣化、マーカー多数) は、いずれも CPU 段が支配的な場面です。
- 統合 GPU で managed / mapped memory を使う最適化 (WP-4.2) は、Phase 3 で転送そのものが消えるなら不要になります。Phase 3 の後に必要性を再判断します。
- 起動の費用は用途で判断が分かれます。連続する動画なら 25 秒程度で元が取れますが、単発の検出では CPU 経路が有利です。この結論は変わりません。

## 未確定事項

- 転送を消した場合に GPU 段がどこまで下がるか。kernel 実行だけなら DGX Spark 0.083 ms、RTX 5070 Ti 0.033 ms、Jetson Orin 0.928 ms である。Phase 3 の完了後に測る。
- 8 回の同期転送を非同期化して重ねられるか。現在は 1 回ずつ blocking する。
- 統合 GPU で転送費用が単体 GPU より大きく出る理由。
- `M-Pinned` と `M-Managed` の値。
- CUDA event による kernel 時間と wall-clock の分離 (WP-4.1)。現在の段階時間は wall-clock であり、host 同期を含む。
- Jetson の CUDA Toolkit は 11.4 (JetPack 5.x)、他 2 機は 13.0。toolkit version の影響は切り分けていない。
- 実写 corpus での測定。現在は合成 corpus のみ。
- 起動の費用を減らせるか。CUDA の文脈生成は減らせないが、kernel の読み込みは
  対象 architecture を 1 つに絞る、または cubin を事前に読み込むことで短縮
  できる可能性がある。DGX Spark の 22.2 ms は 3 つの architecture 向け binary を
  含む fatbin から選ぶ費用を含む。
- 4K を超える解像度。Jetson の crossover がその先にあるかを確かめられていない。

## 測定の再現

```
# container 内で実行する。<cpu> は性能 core の番号。
#   DGX Spark GB10 -> 5   RTX 5070 Ti の機 -> 2   Jetson AGX Orin -> 0
./build/<preset>/tools/corpusgen/aruco3cuda_corpusgen --preset full --seed 20260827 \
  --output-dir /tmp/benchcorpus --manifest /tmp/benchcorpus/manifest.json

B=./build/<preset>/bench/aruco3cuda_bench
COMMON="--warmup 30 --latency-iterations 200 --throughput-frames 100 --cpu-list <cpu> --threads 1"
IMGS="--input /tmp/benchcorpus/clean_640x480_n4_s128.png \
      --input /tmp/benchcorpus/clean_1280x720_n4_s128.png \
      --input /tmp/benchcorpus/clean_1920x1080_n4_s256.png \
      --input /tmp/benchcorpus/clean_3840x2160_n4_s256.png \
      --input /tmp/benchcorpus/clean_1280x720_n1_s128.png \
      --input /tmp/benchcorpus/clean_1280x720_n16_s128.png \
      --input /tmp/benchcorpus/blur_1280x720.png \
      --input /tmp/benchcorpus/noise_1280x720.png \
      --input /tmp/benchcorpus/combined_1280x720.png"

for run in 1 2 3; do
  taskset -c <cpu> $B $IMGS $COMMON --route CPU           --memory-mode N/A        >> results.jsonl
  taskset -c <cpu> $B $IMGS $COMMON --route CUDA-Resident --memory-mode M-Device   >> results.jsonl
  taskset -c <cpu> $B $IMGS $COMMON --route Hybrid        --memory-mode M-Device   >> results.jsonl
  taskset -c <cpu> $B $IMGS $COMMON --route Hybrid        --memory-mode M-Pageable >> results.jsonl
done
python3 bench/aggregate.py results.jsonl
```

実機への同期は `tools/sync-to-host.sh <user@host>` を使います。
