# CPU Optimization Experiment

## Purpose

Determine how far a CPU detector can improve detection latency over the pinned
OpenCV CPU baseline by applying the findings of the CUDA implementation. Changes
must be judged by measured end-to-end detection time and detection compatibility,
rather than by assuming that GPU work decomposition is also efficient on a CPU.

## Scope

The experimental implementation is in `cpu/`, on branch
`experiment/cpu-optimization`. It accepts host `CV_8UC1` images and produces host
IDs and full-resolution corners. The implementation uses OpenCV image processing
operations and this repository's host candidate grouping rules. It does not
execute CUDA kernels or initialize the CUDA runtime.

The installed CUDA API is outside this experiment. This experiment also does not
change the definition of the detection conditions: the ArUco3 detection strategy,
minimum marker size, threshold windows, dictionary, error correction, and corner
refinement settings must agree between the candidate and the baseline.

## Current state

The CPU detector has independent optimization switches, so the compatibility
control and combinations of the proposed changes can be checked on identical
images. The implementation and its provenance are described in the
[module sidecar](../../cpu/cpu_detector.md). The multiwindow threshold operation
has a separate [sidecar](../../cpu/cpu_threshold.md).

The baseline is OpenCV 4.14.0, commit
`0654a42e19215ef25b1d367d822f3c630447e7c7`, built in Release mode, as recorded
in [Code provenance](../code-provenance.md). The experimental tests call its
public `cv::aruco::ArucoDetector` API directly. No official ArUco GPLv3 source is
used. Test markers are generated by the OpenCV predefined Dictionary API, and
degraded scenes by the existing repository corpus generator.

### Candidate changes

| Change | Intended reduction | Compatibility constraint |
| --- | --- | --- |
| Reuse and demand-driven construction of the image pyramid | Allocation and computation for unused pyramid levels | Build the same levels with the same OpenCV border and rounding rules before use |
| Packed dictionary matching | Small temporary buffers and byte-oriented operation calls | Preserve ambiguous-cell masks, first qualifying ID, rotation ties, and error correction |
| Fused cell counting and reusable decode storage | Per-cell views, function calls, and candidate allocations | Preserve the canonical image, Otsu threshold, white-pixel ratios, and low-variance behavior |
| Shared multiwindow threshold workspace | Repeated source traversal and normalized mean images | Match `adaptiveThreshold` pixel for pixel, including isolated ROI borders and budgeted stripe boundaries |
| Compressed contour screening | Point storage for contours rejected by perimeter | Restore the exact unit chain for retained contours before polygon approximation |
| Connected-component size screening | Contour tracing for components too small to survive the perimeter limit | Remove a component only when an upper bound on its unit-chain length is below the configured minimum |
| Filtered contour workspace | Temporary storage and copying of perimeter-ineligible paths | Preserve ordered full paths and every quad decision |
| Sparse current-frame pyramid | Pixels outside actual decoding/refinement footprints | Preserve global coordinates, phase, borders and arithmetic; invalidate validity each frame |
| Geometry work selection | Regional computation overhead on dense candidate layouts | Use current candidate geometry only; never skip candidates |
| Immutable exact-code lookup | Repeated dictionary scans for known definite words | Precompute the complete first-acceptable-ID and rotation result; retain fallback for ambiguity/misses |
| Cached refinement | Repeated Gaussian-mask and patch allocation | Preserve every iteration and sample |
| Spatial grouping bounds | Unnecessary candidate pair metrics | Keep ordering/ties; remains off by default because gains were negligible |

The steady-state defaults enable filtered contours, sparse pyramids, cached
refinement and exact-code lookup in addition to the earlier compatible defaults.
The [follow-up report](../cpu-steady-state-report.md) records their validation,
measurements, rejected alternatives and limitations. No temporal information is
used. The geometry decision chooses only how to compute the same pixels.

The compatibility experiments retain the contour-based detection strategy. An
explicit `component_candidates_` option also tests connected-component and
extreme-point extraction derived from this repository's CUDA design. It is a
separate algorithm experiment: its candidate set, corners, and rejected counts
can differ from OpenCV, and it cannot be enabled as a compatible optimization.
The limitations of that approach are recorded in
[ADR-0003](../adr/0003-candidate-extraction-approach.md). Clean marker recovery is
checked separately against the rendered geometry, without weakening the exact
OpenCV compatibility tests of the contour route.

`CpuOptions::threshold_max_prefix_bytes_` limits the shared threshold integral
owner's payload, including its halo and zero row. Its default is 2 MiB. Positive
budgets use per-stripe padding; zero preserves the earlier whole-image padding
and accumulator-overflow-only stripe plan. A budget too small for even one
output row and its halo selects the OpenCV threshold fallback. This is a prefix
scratch limit, not a total-memory cap: input, output images, padding, other
detector stages, and OpenCV's fallback allocations are separate. Reducing the
budget also releases oversized retained prefix storage before falling back.

### Automated validation

The tests in `test/cpu/` require OpenCV and GoogleTest but no CUDA-capable device.
They cover the following behavior:

- All 91 scenes of the `full` synthetic preset, both with and without the ArUco3
  detection strategy, compared against the OpenCV baseline. Detection IDs,
  corner order (and therefore rotation), corner coordinates, and rejected counts
  are checked for the compatibility control, default compatible optimizations,
  and all compatible switches, with OpenCV thread counts of one, two, and four.
- The 17-family synthetic rotation test (16 NxN families plus MIP), each with the first and last ID at all four
  quarter-turn rotations, with the ArUco3 strategy enabled and disabled.
- Independent optimization combinations, alternate border/cell/threshold
  settings, separate markers carrying the same ID, and OpenCV thread counts of
  one, two, and four.
- Degenerate diagonal and axis-aligned strokes, nested holes, concave polygons,
  touching shapes, and random binary/grayscale noise, comparing both detections
  and the candidate count between the compatibility control and all switches on.
- Repeated input changes, including dimensions, non-contiguous ROI stride, and
  new pixels at an unchanged pointer, to expose stale workspace data.
- Invalid lifecycle, image, dictionary, and configuration inputs.
- Threshold pixel equivalence on random images, constant images, checkerboards,
  one-pixel dimensions, non-contiguous ROIs, fractional and negative constants,
  large windows, sums adjacent to half-integer mean boundaries, and 4K inputs
  whose replicated halo would overflow a single full 32-bit integral image.
- Prefix budgets from one byte through 4 MiB, legacy zero and `SIZE_MAX`, on
  white/random 4K strided ROIs. The same workspace changes budgets and shapes
  repeatedly, and in-place output aliases verify that later stripes still read
  the original input pixels. Public detector results are compared again after
  changing budgets through reinitialization.
- A 96-scene adversarial corpus and changing-frame sequences, including repeated
  pointers and ROIs; direct contour path, fractional warp and monitored refinement
  checks; dictionary lookup ties/ambiguity and reinitialization. The historical
  exhaustive 512-case matrix covers nine switches; new switches have explicit
  isolated and combined tests, not an exhaustive matrix over every new flag.

Tests generate their own corpus files in a process-local temporary directory.
They do not share output files with other tests, and remove their files on exit.
Performance is evaluated separately from these correctness checks.

### Measurement requirements

The experimental benchmark must use the same loaded image for OpenCV and every
candidate. Image loading, checksums, and corpus generation remain outside the
measured detection interval. Report warm-up and measurement counts, independent
process count, CPU affinity, OpenCV thread count and build, compiler options,
power and clock conditions, and other active workloads.

Record per-scene median, p95, and p99 detection latency. Keep initialization,
single-frame latency, and sequential throughput separate. Stage profiling is an
optional diagnostic run; its instrumentation must not silently enter the main
latency figures. CUDA kernel time is not applicable to these host-only routes.
Record memory usage and retained scratch space separately from time. Independent
frame-worker throughput is a distinct experiment with its own CPU budget,
changing inputs, indexed results and every-frame exact checks. Its service
latency excludes queue wait and is not camera-to-result latency.

Measure at least both one thread and a common multi-core budget. Include clean
scenes with detections, empty scenes, noisy scenes with many contours, degraded
markers, and the full-resolution strategy. Report regressions as well as wins.
The earlier 28-scene CUDA timing sweep contains 20 scenes without detections;
it is insufficient by itself to establish CPU decode speedups.

## Goals

- The current follow-up objective is to push steady-state CPU speed while keeping
  accuracy at least equal to OpenCV. Tracking, previous-frame detection reuse,
  temporal predictions, and skipped frames are forbidden. Reusable allocation,
  precomputation and independent-frame video scheduling are allowed. Startup
  latency is recorded when useful but is not an optimization acceptance gate.
- Evaluate remaining contour allocation, spatial grouping, and full-frame pyramid
  costs before declaring a measured frontier. Preserve an explicit previous
  implementation route for paired before/after comparison.
- Extend accuracy gates to changing-frame sequences and additional detectable,
  degraded markers. Exact output equality is sufficient for no accuracy loss;
  any changed-output algorithm needs independent ground-truth evidence for recall,
  precision, ID/rotation, and corner accuracy before it can replace the default.
- Establish compatibility before using performance results to select defaults.
- Retain changes that improve the measured workload and expose explicit options
  where the best choice depends on the scene or machine.
- Keep correctness tests and raw benchmark results reproducible.
- State the observed optimization limit and rejected experiments, without
  claiming a universal limit across unmeasured images and hardware.

## Measurement record

The [CPU benchmark report](../cpu-benchmark-report.md) records the retained
defaults, measured end-to-end latency, independent-process variation, resource
measurements, rejected experiments and remaining bottlenecks. Its local raw
results describe the earlier snapshot; generated outputs are not version-controlled. The
[steady-state follow-up](../cpu-steady-state-report.md) records the later defaults
and must be used for claims about them.

## Open questions

- Nine external regression/photo fixtures have been checked for compatibility
  across all 18 supported dictionaries. They have no independent annotations in
  this experiment and do not establish field accuracy or a real-image speedup.
- The optional component/extrema extractor rejects a four-pixel stroked
  rectangle whose outer corners are beveled by rasterization, although the
  corresponding sharp rectangular frame is accepted. Its inlier and edge
  support gates therefore do not guarantee recovery of every visible quad.
  The automated test records this known limitation separately from clean
  marker recovery. Its effect on real-marker recall remains unmeasured.
- Jetson Orin, Jetson Thor, and x86_64 validation have not been performed for
  this CPU experiment. The available development machine is DGX Spark GB10.
- Current CPU-module coverage and remaining gaps are recorded in the
  [steady-state validation record](../measurements/2026-11-17-cpu-steady-validation/README.md).
  Existing CUDA coverage is not a substitute for this module's results.
- The application-level benefit depends on its stage proportions, marker sizes,
  contour density, OpenCV build, and available CPU cores.
