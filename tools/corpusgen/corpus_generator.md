# corpus_generator

## Purpose

Produces synthetic marker images with corner ground truth, in a form that can be regenerated by fixing the seed. The CPU baseline results are a compatibility baseline, not ground truth, so accuracy evaluation needs ground truth that is known at generation time.

## Scope

Covers generation of the synthetic images, application of the degradation conditions, computation of the ground truth, and output of the manifest. Collection and annotation of real images are out of scope.

## Current state

- There are three presets: `smoke`, `basic`, and `full`.
- The degradation conditions are rotation, projective distortion, blur, noise, illumination gradient, occlusion, and placement that runs off the image border.
- Output is PNG files and a manifest JSON with `schema_version` 1.

## Design decisions

### Ground truth is determined from the input side of the projective transform

The marker image is drawn at a canonical resolution and placed by a projective transform onto the target quadrilateral. The ground truth is the corners of the transform destination themselves; it is not estimated from the generated image. Even with rotation or projective distortion added, the ground truth is exactly determined.

The corners follow the pixel boundary convention. With pixel centers at integer coordinates, the outer edge of a `size` pixel image runs from `-0.5` to `size - 0.5`. OpenCV's detection results follow the same convention.

### Each scene uses an independent random sequence

The random seed is derived from `seed` and the scene's sequence number. If a single random sequence were shared across all scenes, adding just one scene would change the contents of every scene after it, and diffs of the corpus could no longer be followed.

Noise is generated with a custom distribution rather than `cv::randn`. Depending on OpenCV's global RNG state would make the results change with the call order of other processing.

### Degradation is applied to the whole image after placement

Blur, illumination gradient, and noise are applied in that order. Without a fixed order, the same conditions would not yield the same image.

### `side_ratio` is recorded

ArUco3 excludes markers with a small side length at the downscaling stage. The exclusion boundary is not `tau_i` itself but is determined by the following formula.

```
side_px >= S + L * tau_i
```

`S` is `minSideLengthCanonicalImg`, `L` is the long side of the image, and `tau_i` is `minMarkerLengthRatioOriginalImg`. This follows from the requirement that the side length after multiplying by the downscale factor `fxfy = S / (S + L * tau_i)` must be at least `S`. In terms of the side ratio, `side_ratio >= S / L + tau_i`.

`minimum_detectable_side_px()` returns this lower bound. The manifest records the `side_ratio` of each marker, so that it can be determined afterwards at which `tau_i` the marker becomes a detection target.

Exactly at the boundary value, detection can fail because of resampling effects. For 1280x720 with `S = 32` and `tau_i = 0.05` the lower bound is 96 pixels, but in measurements 96 pixels was not detected while 128 pixels was. The `smoke` preset uses dimensions with margin.

### Images are not committed to the repository

The generated files are large, so they are not committed; the manifest records their storage location and checksum.

## Goals

- Allow real images to be registered in the manifest under the same schema.
- Avoid duplicate marker IDs, so that correspondence by ID is unique.
- Match the scale and generation time of the `full` preset to the measurement conditions of the evaluation plan.
